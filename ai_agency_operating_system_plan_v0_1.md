# AI Agency Operating System Plan v0.1

## Purpose

This document captures the starter plan for building a US-based design agency that uses AI agents responsibly across the marketing, intake, and delivery pipelines.

The goal is to build the **board-guided operating system first** before spending money on heavier coding tools. That means creating a strong foundation for:
- shared context
- workflow specifications
- evaluation
- testing
- reusable templates
- gradual automation

This is not a “launch a bunch of agents fast” plan.  
It is a **build the operating system first** plan.

---

# 1. Agency Constitution v0.1

## Purpose
We help companies improve digital products, service experiences, and internal workflows through structured UX, service design, and AI-enabled operating systems.

We do not sell AI hype.  
We sell:
- clearer decisions
- faster delivery
- better user experiences
- better business operations

## Positioning
We are a high-trust, strategy-led design agency that uses AI to increase speed, consistency, and quality.

We combine:
- UX and service design thinking
- business analysis
- workflow and system design
- AI-assisted research, documentation, and production

We are not:
- a commodity design subscription
- a vague prompt agency
- a replacement for client teams

We help clients understand, improve, and scale their experience and operating systems.

## Mission
Build a modern agency that can deliver excellent strategy and design work with a smaller team by using AI agents, structured context, and evaluation systems responsibly.

## Core Principles
- Truth over polish
- Systems over chaos
- Reusable context over repeated effort
- Evidence over opinion
- Clear specs over vague requests
- Human judgment at key decisions
- Automation only after process stability
- Quality must be testable

## Ideal First Clients
Best-fit clients are:
- US-based
- small to midsize companies
- B2B SaaS teams
- operations-heavy businesses
- consulting businesses
- enterprise internal teams with workflow or experience complexity

## Initial Offers
Start with only 3 offers:
1. UX / service experience audit
2. AI workflow and operating system design
3. Strategic redesign / optimization engagement

## What We Refuse
We do not take:
- pure logo-only branding projects
- low-budget custom software builds
- clients who want total automation with no human accountability
- unclear projects with no owner
- projects where success cannot be defined
- high-chaos clients who refuse process

## Client Promise
Clients should feel:
- understood quickly
- guided clearly
- confident in next steps
- impressed by structure
- supported by evidence, not fluff

## Quality Standard
A deliverable is not done because it looks good.  
It is done when it:
- answers the business problem
- reflects user reality
- fits the scope
- is easy to act on
- is internally consistent
- can be defended logically

## Human-in-the-Loop Rule
AI may:
- draft
- summarize
- structure
- score
- recommend

A human approves:
- qualification decisions
- final proposals
- pricing
- major strategy calls
- final client-facing deliverables

# 5. First 6 Operating Specs

## Spec 1 — Content Brief Generation
**Purpose**  
Turn strategic priorities into clear content briefs.

**Trigger**  
A content idea is moved to Prioritized.

**Inputs**
- ICP record
- offer record
- current campaign theme
- voice rules
- proof assets or case studies
- CTA objective

**Required Output**
- title/hook
- audience
- pain point
- desired action
- content angle
- proof points
- structure outline
- CTA
- confidence
- missing context list

## Spec 2 — Inbound Lead Qualification
**Purpose**  
Determine whether a lead is worth discovery.

**Trigger**  
A new lead enters intake board.

**Inputs**
- lead form
- enrichment data
- ICP catalog
- offer catalog
- qualification rubric
- red flag rules

**Required Output**
- fit score
- confidence score
- top 3 reasons
- top red flags
- missing info
- recommended next step

## Spec 3 — Discovery Call Summary and Structuring
**Purpose**  
Convert messy notes or transcript into decision-grade opportunity context.

**Trigger**  
A discovery call completes.

**Inputs**
- transcript
- notes
- lead/opportunity record
- discovery framework
- scoping rules

**Required Output**
- business problem summary
- goals
- pain points
- current-state issues
- stakeholders
- constraints
- urgency
- desired outcomes
- unclear items
- recommended offer path

## Spec 4 — Proposal Assembly
**Purpose**  
Generate a proposal draft from qualified opportunity context.

**Trigger**  
Opportunity moves to Scoping.

**Inputs**
- approved discovery summary
- offer template
- pricing rules
- exclusions library
- proposal blocks
- risk rules

**Required Output**
- proposal summary
- scope
- outcomes
- deliverables
- assumptions
- exclusions
- timeline
- pricing recommendation
- risk notes
- negotiation watchouts

## Spec 5 — Project Kickoff Brief
**Purpose**  
Create a complete internal context pack for delivery.

**Trigger**  
Proposal becomes won.

**Inputs**
- final proposal
- discovery summary
- client communications
- delivery standards
- project template

**Required Output**
- project objective
- success metrics
- scope summary
- exclusions
- stakeholders
- dependencies
- risks
- milestones
- required client inputs
- first sprint recommendations

## Spec 6 — Deliverable QA Review
**Purpose**  
Check work before it reaches the client.

**Trigger**  
Deliverable enters Internal QA.

**Inputs**
- deliverable draft
- project brief
- acceptance criteria
- QA rubric
- client tone/style rules

**Required Output**
- QA score by dimension
- issues list
- severity
- exact revision recommendations
- approval status

# 6. Evaluation Structure

Every workflow should be scored on:
- Accuracy
- Completeness
- Business Relevance
- Consistency with Agency Standards
- Actionability

## Failure Taxonomy
When something goes wrong, tag it as:
- Context gap
- Spec gap
- Prompt gap
- Model reasoning issue
- Human review gap
- Data structure issue
- Template issue

---

# 7. Automated Testing Structure

Before spending on advanced tooling, create tests in plain language.

## Test Types
- Happy path
- Missing information
- Contradictory information
- Out-of-scope request
- Bad fit lead
- Ambiguous discovery notes
- Tight deadline / unrealistic ask
- Formatting challenge

## Minimum Tests Per Spec
- 5 happy path
- 3 edge cases
- 2 failure injection cases

# 9. 30-Day Build Sequence

## Week 1
Define:
- agency niche
- first offer
- ICP
- success metrics
- board structure

## Week 2
Write:
- context schema
- first 6 workflow specs
- stage definitions
- ownership rules

## Week 3
Create:
- sample records
- gold-standard outputs
- evaluation rubrics
- test cases

## Week 4
Dry-run everything manually:
- simulate leads
- simulate discovery
- simulate proposal creation
- simulate project delivery
- simulate QA review
- identify missing context or spec gaps

Only after that should you decide whether advanced coding tooling is worth paying for.

---

# 10. What Not To Do Yet

Do not prioritize these first:
- buying multiple agent tools
- overbuilding multi-agent orchestration
- connecting too many apps
- making the board visually fancy
- trying to automate pricing end-to-end
- creating dozens of agents before one spec is stable

Your first goal is a reliable manual-plus-AI operating model.
